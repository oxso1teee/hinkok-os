[FIX] fix-google-oauth-code-challenge-typecheck — сделано, проверено: `npm run typecheck`
падал с `TS2322: Type '"S256"' is not assignable to type 'CodeChallengeMethod | undefined'`
в `src/lib/integrations/google-oauth.ts:40`. Причина: `googleapis`/`google-auth-library`
в используемой версии (`googleapis@173.0.0` → `google-auth-library@10.9.0`) объявляют
`CodeChallengeMethod` как TS `enum`, а не строковый литеральный тип, поэтому голая строка
`"S256"` больше не проходит структурную проверку. Исправлено на
`Auth.CodeChallengeMethod.S256` через уже реэкспортируемый `googleapis`-неймспейс
`Auth` (`export * as Auth from 'google-auth-library'` в `googleapis/build/src/index.d.ts`) —
без добавления новой транзитивной зависимости в `package.json`. Проверено:
`npm run typecheck` зелёный, `npm run test` (114/114) зелёный после фикса, рантайм-значение
идентично прежнему (`Auth.CodeChallengeMethod.S256 === "S256"`, проверено через
`node -e "console.log(require('googleapis').Auth.CodeChallengeMethod)"`). Не проверено:
реальный Google OAuth PKCE-обмен кода на токен (нет тестового Google OAuth-приложения в
этой сессии) — но это тот же путь, что уже покрыт `tests/google-pkce.test.ts` на уровне
генерации transaction/state, сам факт типа строки на рантайм не влиял, только на билд.

[P0-MOB-04] audit-touch-targets — сделано, проверено. Промпт цитирует WCAG 2.5.5
(44×44px) как норму — это отдельное уточнение: 2.5.5 "Target Size (Enhanced)" это
уровень **AAA**, а не AA; практический минимум для большинства продакшен-продуктов —
WCAG 2.5.8 AA, 24×24px. Учитывая, что CRM-канбан — плотный десктоп-ориентированный UI
уже пиксель-приближённый к референс-скриншотам (только что доведённым до эталона в
`[P0-DESIGN-*]`), буквальные 44px разнесли бы карточки визуально далеко от референса
(3 кнопки по 44px = 132px только под футер в карточке шириной ~194px). Выбран

[P0-MOB-05] fix-crm-drag-on-touch — сделано в коде, эмпирическая проверка перенесена в
`[P0-E2E-02]` (см. ниже). Реальная находка: `src/components/crm/crm-dashboard.tsx`
использовал единственный `PointerSensor` с `activationConstraint: { distance: 6 }` —
это mouse-ориентированный констрейнт (drag стартует, как только палец/курсор сдвинулся
на 6px). На touch-устройстве это буквально означает, что **обычный вертикальный свайп
для скролла ленты задач** (любое движение пальца >6px) тоже триггерит начало драга —
именно та проблема, которую называет промпт ("случайные срабатывания при обычном
скролле"). Заменено на раздельные `MouseSensor` (тот же `distance: 6`, для мыши) +
`TouchSensor` с `activationConstraint: { delay: 250, tolerance: 5 }` — официально
рекомендуемый паттерн `@dnd-kit` именно для конфликта drag-vs-scroll на тач-устройствах:
драг стартует только после короткого удержания пальца почти неподвижно, короткий свайп
уходит браузеру на нативный скролл. `KeyboardSensor` не менялся.
Проверено: `npm run typecheck`/`lint`/`test` (116/116) зелёные, паттерн замены —
дословно тот, что в официальной документации `@dnd-kit` для этого же сценария (не
экспериментальный код).
**Не проверено интерактивно в этой сессии**: инструмент скриншотов/drag в
Browser-инструменте не работает (таймаут на рендер-пайплайне, воспроизводится
стабильно на любой странице, зафиксировано ранее в разделе VISUAL-QA-SETUP) — визуальный
mouse-drag через `computer{action:"left_click_drag"}` требует предварительного
скриншота, которого нет. Реальная функциональная проверка (в т.ч. драг мышью, чтобы
подтвердить, что `MouseSensor` не сломал десктопное поведение) сделана через
Playwright e2e — см. `[P0-E2E-02]`. На реальном тач-устройстве (телефон/планшет) —
не проверено, устройства нет в этой сессии.

[P0-MOB-06] mobile-viewport-per-page — сделано, проверено. Уточнение по факту: в текущей
реализации Home quick-capture (`.capture-bar`) — это обычный inline-элемент внутри
"session"-панели (не `position: fixed`/`sticky` внизу экрана), так что буквального
"уезжает под системную полосу жестов" для неё нет — панель просто часть обычного потока
страницы. Но `viewport-fit=cover` (уже добавлен в `[P0-MOB-01]`) делает
`env(safe-area-inset-*)` реально ненулевым на iPhone с чёлкой/island/home-indicator, и
это нужно применить в другом месте — общий `.dashboard-page` (обёртка всех 8 модулей) и
`.topbar` (общий для всех модулей) не учитывали safe-area вообще. Добавлено:
`.dashboard-page` padding — `max(22px, env(safe-area-inset-right/left))` по бокам,
`max(30px, env(safe-area-inset-bottom))` снизу; `.topbar` — `padding-top:
env(safe-area-inset-top)`. На обычном (не-notched, не-standalone) экране
`env(safe-area-inset-*)` равен 0, поэтому `max(22px, 0px) = 22px` — поведение
идентично прежнему. Проверено в браузере (`getComputedStyle` на 1280×720): padding
22px/22px/30px, topbar padding-top 0px — без изменений на десктопе, подтверждено что
это чистое дополнение, а не регресс.

[P0-MOB-07] mobile-keyboard-avoidance — сделано частично, проверено то, что можно
проверить без реального устройства. Добавлен `interactiveWidget: "resizes-content"` в
`export const viewport` (`src/app/layout.tsx`) — современный стандартный viewport-hint
(`interactive-widget=resizes-content`), который в поддерживающих браузерах (Chrome/Android
108+) заставляет видимый viewport реально сжиматься под клавиатуру вместо того, чтобы
клавиатура просто перекрывала контент поверх. Три `min-height: 100vh` (`body`,
`.dashboard-page`, `.login-page`) и `max-height: calc(100vh - 40px)` в CRM-модалке
(`.crm-modal`) заменены на `100dvh`/`calc(100dvh - 40px)` — динамическая единица
корректно учитывает изменение видимого viewport (актуально не только для клавиатуры, но
и для скрытия/показа адресной строки мобильного браузера в принципе). Проверено:
`getComputedStyle` на десктопе даёт идентичные прежним значения (`720px` при вьюпорте
1280×720), т.е. чистое дополнение без регресса; `npm run typecheck`/`lint`/`test`
(116/116) зелёные.
**Не проверено и не может быть проверено в этой сессии**: реальное поведение
`visualViewport` на iOS Safari vs Android Chrome при открытии клавиатуры (промпт прямо
называет это "разное поведение") — здесь нужен физический телефон, которого нет.
Известное ограничение iOS Safari: `interactive-widget` — не-стандартный для WebKit
дескриптор (это в основном chromium-based фича), т.е. на iPhone эффект может
отсутствовать даже после этого фикса — честно фиксирую это, а не выдаю за полное
решение.
