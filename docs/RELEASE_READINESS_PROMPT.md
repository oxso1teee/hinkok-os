# HinkoK OS — мастер-промт «до продакшена на 10000%»

Этот файл — техзадание для AI-агента (Claude Code / Cursor / Codex-агент), который будет
доводить проект `HinkoK OS` (Next.js 16 + Supabase + pgvector, персональная AI-ОС) до
состояния «можно реально пользоваться каждый день и не бояться, что что-то отвалится».

Документ построен по аудиту реального кода из архива `HinkoK-OS-Phase2-Block6-google-complete.zip`
и файла `HinkoK_OS_Guide.md`. Ссылки на файлы — реальные пути в репозитории, не выдуманные.

## 0. Как этим пользоваться

- Каждый пункт — отдельная задача. У задачи есть ID (`[P0-AUTH-01]` и т.п.), формулировка,
  критерий «сделано» (definition of done) и, где нужно, конкретные файлы для правки.
- **«Сделано» = реально проверено.** Не «должно работать», а: запущен `npm run typecheck`,
  `npm run lint`, `npm run test`, `npm run build`, при необходимости `npm run e2e`, и
  вручную пройден сценарий. Если агент физически не может проверить (нет доступа к реальному
  Supabase/Telegram/Google), он обязан прямо это написать, а не делать вид, что всё ок.
- Приоритеты: **P0** — блокирует релиз в продакшен для реального ежедневного использования.
  **P1** — сильно влияет на надёжность/удобство, делать сразу после P0. **P2** — качество жизни,
  можно после первого стабильного релиза.
- Порядок выполнения внутри приоритета — сверху вниз, но блоки независимы, можно параллелить.
- Если в процессе находится противоречие между этим файлом, `README.md`, `docs/*.md` и реальным
  кодом — не выбирать самому, а зафиксировать расхождение отдельным пунктом в отчёте и продолжить
  с тем поведением, которое сейчас в коде (код — источник истины по факту, доки — по намерению).
- Именование новых файлов/функций — `kebab-case`, паттерн «действие+объект»
  (`refresh-google-token.ts`, `verify-backup-passphrase.ts`), в духе уже существующего кода.
- Каждая найденная нетривиальная развилка/воркараунд — фиксировать отдельной строкой в
  `docs/CHANGELOG_AGENT.md` (создать, если его нет), а не только в коде.

## 1. Текущее состояние проекта (аудит на момент написания)

Что уже реально есть и работает по коду (не по READ ME-заявлениям, а по факту наличия кода):

- Next.js 16 App Router, TypeScript strict, ESLint 9, Tailwind 4 с кастомными CSS-переменными.
- Одностраничные модули: `home`, `crm`, `brain`, `journal`, `health`, `operations`, `settings`,
  `backup`, `login` — у каждого свой `page.tsx`, `*.css` и `*-dashboard.tsx` компонент.
- 28 API-роутов под `src/app/api/**`.
- Однопользовательская модель: один `USER_ID`, один `DASHBOARD_PASSWORD`, HMAC-подписанная
  сессия-кука, `proxy.ts` как edge-гейт + повторная проверка внутри страниц/роутов.
- Supabase Postgres + pgvector, 17 миграций в `supabase/migrations/`, все с deny-all RLS для
  анонимной/браузерной роли — доступ только через service role на сервере.
- Захват мыслей: Telegram webhook (текст, голос, фото) → трёхступенчатый классификатор
  (Anthropic → OpenAI Structured Outputs → regex-фолбэк) → атомарная маршрутизация в задачи/
  дневник/питание/календарь.
- RAG: `ask/route.ts` — pgvector-поиск + Anthropic/OpenAI с фолбэком на экстрактивный ответ.
- Интеграции: Google Calendar (OAuth PKCE + сервис-аккаунт фолбэк), Google Sheets (финансы),
  Obsidian через приватный GitHub-репо, Apple Health через iOS Shortcuts.
- Крон-джобы: sync-calendar, sync-obsidian, weekly insights — с Bearer-секретом, advisory locks,
  дедупликацией и `operations`-дашбордом статусов джобов.
- Бэкап: AES-256-GCM экспорт с scrypt KDF, dry-run восстановление.
- CI: `npm run ci` — repo-check, `npm audit`, typecheck, lint, test, build. GitHub Actions с
  pinned SHA экшенами, Dependabot.
- Тесты: 29 unit/integration тестов (`tests/*.test.ts`, `node:test`), **1** Playwright e2e-спек
  (`e2e/authentication.spec.ts`) + axe-сканы accessibility только на логине.
- CSS: медиа-запросы есть в каждом `*.css` (2–4 брейкпоинта на файл), но нет ни одного
  `manifest.json`, service worker, PWA-иконок — то есть «мобильная версия» пока = адаптивная
  вёрстка в браузере, а не устанавливаемое приложение.

Что явно отсутствует или не завершено (база для P0/P1 ниже):

- Нет восстановления пароля/доступа — только один статический `DASHBOARD_PASSWORD` в `.env`.
- Нет 2FA/второго фактора.
- Нет PWA-манифеста, иконок, service worker, offline-заглушки.
- E2E-покрытие — только логин, ни один из 8 функциональных модулей не покрыт браузерными тестами.
- Нет визуального регресс-тестирования (только axe для WCAG).
- Нет observability-слоя (error tracking типа Sentry, structured logging, uptime-алертов) —
  только приватный `operations`-дашборд по кроном-джобам.
- Нет rate-limit/abuse-защиты на уровне Vercel/edge (только БД-rate-limit внутри роутов).
- Нет staging-окружения и процедуры отката релиза.
- Нет пользовательской документации/онбординга («как пользоваться», не «как задеплоить»).
- Нет политики хранения/удаления данных и экспорт-в-один-клик для самого пользователя из UI
  (бэкап есть, но это не то же самое, что «удалить меня» или «показать что вы обо мне храните»).
- Нет нагрузочного тестирования (сколько захватов/сек выдержит webhook, сколько стоит embedding
  при реальном объёме заметок).

## 2. P0 — блокеры перед тем, как реально жить в приложении каждый день

### 2.1 Аутентификация и «регистрация»

Важное уточнение архитектуры, которое нужно явно принять как решение, а не молча
проигнорировать: проект **намеренно однопользовательский** (`USER_ID` — константа окружения,
не таблица пользователей). Полноценная регистрация/мультиаккаунтность — это смена архитектуры,
а не баг. Ниже — два трека: (A) довести однопользовательский вход до продакшн-уровня надёжности,
(B) опционально — путь к мультиаккаунтности, если она реально нужна (например, чтобы пустить
партнёра/помощника с ограниченным доступом).

**Трек A — обязательный (P0):**

- `[P0-AUTH-01] add-password-recovery-flow` — сейчас единственный способ сменить
  `DASHBOARD_PASSWORD` — руками поменять переменную окружения и передеплоить. Добавить:
  - Второй секретный recovery-код (генерируется вместе с `AUTH_SECRET`/`API_SECRET` через
    `scripts/generate-secrets.mjs`), который позволяет через отдельный защищённый роут
    (`/api/auth/recover`) выпустить одноразовую ссылку смены пароля, если основной пароль забыт.
  - Recovery-код хранится только как хэш (как минимум SHA-256 + соль, лучше — тот же
    constant-time compare, что уже используется в `src/lib/auth/constant-time.ts`).
  - DoD: сценарий «забыл пароль → восстановил доступ без пересборки `.env` вручную на сервере»
    проверен end-to-end локально.
- `[P0-AUTH-02] add-totp-second-factor` — добавить опциональный TOTP (RFC 6238) поверх пароля:
  новая таблица `auth_totp_secrets` (миграция `2026071900xx_auth_totp.sql`), сид-фраза
  генерируется и показывается один раз с QR-кодом, дальнейший вход требует пароль + 6-значный
  код. Флаг `TOTP_ENABLED` в `settings`, чтобы можно было включать/выключать из UI Settings.
  - DoD: включение 2FA, вход с кодом, инвалидация кода после использования (защита от replay),
    покрыто unit-тестом на проверку окна времени (±1 шаг, обычно 30 сек).
- `[P0-AUTH-03] session-device-list` — сейчас сессия одна кука без видимости, кто/когда
  залогинен. Добавить в Settings/Operations список активных сессий (IP, user-agent, дата входа,
  дата последней активности) и кнопку «завершить все сессии кроме текущей».
- `[P0-AUTH-04] harden-login-rate-limit` — текущий IP-based троттлинг (8 попыток / 15 минут,
  `src/lib/auth/login-attempts.ts`) обходится сменой IP/через VPN. Добавить дополнительный
  глобальный лимит по аккаунту (не по IP) с экспоненциальной задержкой и алертом в Telegram
  владельцу при N неудачных попытках подряд («кто-то ломится в твой дашборд»).
- `[P0-AUTH-05] rotate-secrets-runbook` — написать `docs/SECRET_ROTATION.md`: пошагово, как
  безопасно поменять `AUTH_SECRET`, `API_SECRET`, `DASHBOARD_PASSWORD`,
  `GOOGLE_TOKEN_ENCRYPTION_KEY`, `TELEGRAM_WEBHOOK_SECRET`, `CRON_SECRET` без даунтайма и без
  инвалидации бэкапов (особое внимание на `GOOGLE_TOKEN_ENCRYPTION_KEY` — смена ключа ломает уже
  сохранённые зашифрованные Google-токены, нужен план миграции/ре-энкрипта).
- `[P0-AUTH-06] audit-cookie-flags-in-prod` — проверить, что в реальном Vercel-деплое (не только
  в тестах) кука реально `__Host-`-префикс, `Secure`, `HttpOnly`, `SameSite=Strict`; добавить это
  в `scripts/smoke-deployment.ts` как проверяемый пункт, а не только в security-чеклист README.

**Трек B — опциональный, только если реально нужен второй человек с доступом:**

- `[P2-AUTH-07] design-multi-tenant-path` — не реализовывать сразу, а зафиксировать в
  `docs/MULTI_USER_OPTION.md`: как бы выглядела миграция `USER_ID`-константы в таблицу
  `accounts` с ролями (owner/guest), что сломается (RLS-политики, Obsidian-мэппинг, Telegram
  `TELEGRAM_USER_ID`, крон-джобы). Это план на будущее, не задача этого релиза.

### 2.2 Мобильная версия

Сейчас «мобильная версия» — это только `@media`-запросы в CSS. Для реального ежедневного
использования (человек тыкает в телефон, а не открывает браузер) этого мало.

- `[P0-MOB-01] add-pwa-manifest` — создать `public/manifest.json` (name, short_name,
  `theme_color` из тёплой янтарной палитры проекта — см. `docs/DESIGN_DIRECTION.md`,
  `display: standalone`, `start_url: /`, набор иконок 192/512/maskable), подключить в
  `src/app/layout.tsx` через `metadata.manifest`.
- `[P0-MOB-02] generate-app-icons` — сгенерировать полный набор иконок (favicon, apple-touch-icon,
  PWA 192/512, maskable) на основе текущего лого-плейсхолдера `H` (`login-mark` в
  `src/app/login/page.tsx` — сейчас это буква в кружке, нужно свести к единому арт-дирекшену).
- `[P0-MOB-03] add-service-worker-offline-shell` — минимальный service worker (можно через
  `next-pwa`-подобный подход руками, без лишних зависимостей, раз пакет
  `overrides`/`dependencies` в `package.json` держится минималистичным) — кэшировать app-shell,
  показывать offline-заглушку вместо белого экрана при обрыве связи в метро/лифте.
- `[P0-MOB-04] audit-touch-targets` — пройтись по всем интерактивным элементам в
  `home-dashboard.tsx`, `crm-dashboard.tsx` (особенно drag-and-drop карточки — `@dnd-kit`),
  `journal-dashboard.tsx`, `brain-dashboard.tsx`: минимальный размер тач-таргета 44×44px
  (WCAG 2.5.5), особенно кнопки урджентности задач и колонки канбана в CRM.
- `[P0-MOB-05] fix-crm-drag-on-touch` — явно перепроверить, что `@dnd-kit` drag-and-drop в CRM
  реально работает на реальном тач-устройстве (не только через `TouchSensor`-эмуляцию в тестах):
  скролл колонки во время драга, случайные срабатывания при обычном скролле ленты задач.
- `[P0-MOB-06] mobile-viewport-per-page` — проверить `viewport` meta и `safe-area-inset` для
  iPhone с чёлкой/island (particularly для нижней панели быстрого захвата в Home — `quick capture`
  инпут в `home-dashboard.tsx` не должен уезжать под системную полосу жестов).
- `[P0-MOB-07] mobile-keyboard-avoidance` — формы захвата (Home quick capture, CRM создание
  задачи, Journal редактор) не должны перекрываться открытой мобильной клавиатурой; проверить на
  iOS Safari и Android Chrome отдельно (разное поведение `visualViewport`).
- `[P1-MOB-08] add-pull-to-refresh` — на дашбордах, где данные могут устареть между открытиями
  (Home, CRM, Health), добавить pull-to-refresh или явную кнопку обновления, видимую с одного
  тапа большим пальцем (нижняя треть экрана).
- `[P1-MOB-09] responsive-audit-per-css` — по каждому `*.css` файлу (`home`, `crm`, `brain`,
  `journal`, `health`, `operations`, `settings`, `backup`) пройти три брейкпоинта руками
  (390px iPhone SE/mini, 768px iPad, 1440px desktop) со скриншотами до/после, зафиксировать в
  `docs/design-references/` рядом с существующими референсами.
- `[P1-MOB-10] telegram-as-primary-mobile-path` — учитывая, что основной канал деплоя — Telegram,
  явно прогнать полный пользовательский путь только через бота на телефоне (без открытия сайта)
  и убедиться, что дашборд нужен только для аналитики/настроек, а не для базового захвата.

### 2.3 E2E- и регрессионное покрытие

Сейчас `e2e/authentication.spec.ts` — единственный файл. Это значит, что баг в CRM/Journal/Health
можно словить только руками. Нужно закрыть основные пользовательские сценарии.

- `[P0-E2E-01] add-home-dashboard-spec` — `e2e/home-dashboard.spec.ts`: логин → загрузка Home →
  quick capture текста → появление в соответствующем модуле → отметка привычки → чек, что
  повторный клик не дублирует запись (идемпотентность на UI-уровне).
- `[P0-E2E-02] add-crm-dashboard-spec` — `e2e/crm.spec.ts`: создание задачи, drag-and-drop между
  колонками (мышью и через клавиатуру — `@dnd-kit` поддерживает keyboard sensor, проверить, что
  UI это тоже отражает для accessibility), фильтры по категории/приоритету, поиск, завершение
  задачи и восстановление из архива, проверка optimistic rollback при смоделированной 500-ошибке
  API (перехват запроса в Playwright и форс-фейл).
- `[P0-E2E-03] add-journal-dashboard-spec` — создание записи дня, повторное открытие в тот же
  день не создаёт вторую запись (atomic one-entry-per-day), mood-трекер, вставка prompt-подсказки.
- `[P0-E2E-04] add-brain-dashboard-spec` — рендер 9 сфер, «Ask the OS» с замоканным
  `/api/ask`-ответом, briefing по сфере.
- `[P0-E2E-05] add-health-dashboard-spec` — рендер метрик с фикстурой данных, явные empty-state
  проверки, когда Apple Health не настроен (не должно быть «выдуманных» значений — это заявлено
  в README как принцип, нужно реально протестировать, что фронт не рисует плейсхолдерные цифры).
- `[P0-E2E-06] add-settings-dashboard-spec` — смена идентичности/фокуса/целей, валидация лимитов
  полей, сохранение и повторная загрузка с проверкой персистентности.
- `[P1-E2E-07] add-backup-dashboard-spec` — экспорт с паролем, попытка verify с неверным паролем
  (должна падать явно), dry-run восстановления (без реальной записи в БД в e2e-окружении).
- `[P1-E2E-08] extend-axe-scans-to-all-pages` — сейчас axe гоняется только на логине
  (`e2e/authentication.spec.ts`), расширить на все 8 модулей + фиксировать в CI как gate
  (`npm run ci`), не только смоук.
- `[P1-E2E-09] add-visual-regression` — Playwright screenshot-сравнение по ключевым состояниям
  (пустой Home, заполненный Home, канбан с 20+ карточками) — ловит вёрсточные регрессии, которые
  axe и функциональные тесты не видят.
- `[P2-E2E-10] add-mobile-emulation-suite` — прогнать весь e2e-набор ещё и в Playwright mobile
  Chromium/WebKit-профилях (не только desktop Chromium, как сейчас).

## 3. Модуль HOME — доработки и баги

Файлы: `src/app/page.tsx`, `src/components/home/home-dashboard.tsx`, `src/lib/home/*`.

- `[P0-HOME-01] verify-quick-capture-error-surface` — при ошибке классификации/сохранения
  (провайдер AI недоступен, БД недоступна) пользователь должен увидеть явное сообщение «не
  сохранено, попробуй ещё раз» с возможностью повторить последний текст без перепечатывания —
  сейчас проверить, действительно ли инпут не очищается при ошибке (частая UX-дыра).
  - DoD: смоделирован фейл `/api/captures` (мок 500), подтверждено, что текст остаётся в поле.
- `[P0-HOME-02] audit-degraded-capture-visibility` — README упоминает статус `degraded` для
  захватов при сбое индексации в память. Проверить, что пользователь **видит** этот статус в UI
  Home/CRM, а не только в БД — иначе «незаметный» баг превращается в тихую потерю данных.
- `[P1-HOME-03] add-weekly-goal-progress-bar` — цели недели/месяца сейчас пишутся/читаются, но
  визуальный прогресс (не просто текст) сделает модуль реально полезным для беглого взгляда.
- `[P1-HOME-04] cache-home-data-optimistically` — при быстром повторном открытии Home (например,
  переключение между вкладками телефона) не должно быть полного лоадера каждый раз — держать
  последний успешный снэпшот в клиентском состоянии (не localStorage — см. правило про
  артефакты, но здесь это полноценное Next.js приложение, не артефакт, так что
  `sessionStorage`/React Query-подобный кэш допустим и уместен).
- `[P1-HOME-05] verify-timezone-edge-cases` — `USER_TIMEZONE=Europe/Riga` (или заданная) — Home
  показывает «сегодня»/дедлайны; проверить полночь-переходы и переход на летнее/зимнее время не
  сдвигают задачи на соседний день.
- `[P2-HOME-06] add-keyboard-shortcuts` — быстрый захват по хоткею (например `/` или `c`) для
  десктоп-пользователей, которые держат вкладку открытой весь день.

## 4. Модуль CRM

Файлы: `src/app/crm/*`, `src/components/crm/crm-dashboard.tsx`, `src/lib/crm/*`.

- `[P0-CRM-01] stress-test-optimistic-rollback` — `src/lib/crm/optimistic.ts` реализует

## 22. Визуальный дизайн — довести до эталона по референсным скриншотам

К этому файлу приложены 4 референс-скриншота реального демо HinkoK OS (BRAIN, JOURNAL×2, CRM) —
это **эталон качества и цвета**, к которому нужно привести все страницы. Сейчас, судя по коду
(`docs/DESIGN_DIRECTION.md`, `*.css` файлы), стиль в целом заложен верно (тёплая янтарная
палитра), но нужно свести каждую страницу к пиксель-приближённому соответствию референсам —
и там, где страница выглядит «более сыро», чем референс, — дотянуть.

### 22.1 Разбор референсов (что именно должно быть эталоном)

**Общий каркас (все страницы):**
- Тёмный тёплый градиентный фон: от почти чёрно-коричневого по краям к насыщенному
  янтарно-оранжевому свечению к центру/верху — не плоский цвет, а мягкий radial/linear glow.
- Верхний бар: слева лого `● HinkoK·OS` + версия `/ v3.1` мелким серым, дальше горизонтальный
  нав `HOME · CRM · BRAIN · JOURNAL · HEALTH` (активный пункт — подчёркнут оранжевой линией снизу,
  остальные — приглушённо-серые капсом), справа — тикер живых значений
  (`BTC $64,225 ▲`, `NDX 29,636 ▲`, `XAU $4,239 ▲`) и дата/время (`JUN 13 2026 · 18:28`),
  всё капсом, мелким моноширинным/технич. шрифтом с трекингом (letter-spacing) между буквами.
- Микро-лейблы разделов (`// ask the os`, `SPHERES`, `OPEN TASKS (3)`, `NOTES (18)`,
  `AI · SUMMARY`, `AI BRIEFING`) — всегда капсом, мелкие, с широким трекингом, приглушённый
  серо-оранжевый цвет, часто с префиксом `//` или `/ 01` как «номер блока».
- Большой заголовок страницы — крупный, жирный serif/display шрифт, обычная часть текста белая,
  акцентное слово — курсивом и ярко-оранжевым цветом (`notes that keep thinking.` — «keep
  thinking» оранжевым курсивом; `people, moving.` — «moving» оранжевым курсивом). Это паттерн
  «два слова, второе — акцент» нужно повторить консистентно на всех страницах, где такого пока нет.
- Карточки/панели — скруглённые углы, тонкая полупрозрачная граница (border), фон чуть темнее
  общего градиента, лёгкая тень/glow у активных/выделенных элементов (не плоские flat-карточки).
- Кнопки основного действия (`ASK`, `+ NEW`, `SAVE ENTRY`, `GENERATE`, `SEARCH`) — капсульные
  (полностью скруглённые), градиент от тёплого оранжевого к более светлому/жёлтому, тёмный текст
  на кнопке (не белый) для контраста с ярким фоном кнопки.

**BRAIN (скриншот 1):**
- Строка статистики под заголовком: `9 SPHERES · 18 OPEN TASKS · 52 NOTES · 221 OBSIDIAN` —
  крупные цифры, мелкий капс-лейбл под каждой, плюс кнопка `↻ REFRESH OBSIDIAN` справа.
- Блок «ask the os» — широкий инпут на всю ширину с плейсхолдером-примером в скобках
  (`Ask anything — "what di...`) и капсульная кнопка `ASK` справа, лейбл `MEMORY · RAG` в
  правом верхнем углу блока мелким текстом.
- Ряд из 9 карточек сфер (Work, Finance, Health, Relationships, Growth, Mind, Personal, Content,
  Spirituality) — у каждой: номер (`01`–`09`), название, счётчик задач/заметок мелким текстом.
  Активная/выбранная сфера — с оранжевой обводкой и слегка приподнятым фоном, остальные —
  приглушённые, полупрозрачные, без обводки.
- Блок выбранной сферы: заголовок сферы + лейбл `OPERATIONAL` справа, `AI BRIEFING` с описанием
  и капсульной кнопкой `GENERATE`, список `OPEN TASKS (n)` с чекбоксами/маркерами, список
  `NOTES (n)` с датой заметки, названием жирным и превью текста серым, обрезанным по ширине.

**JOURNAL (скриншоты 2 и 4):**
- Верхний блок `how are you?` — горизонтальный ряд из 5 эмодзи-смайлов (rad/good/meh/bad/awful)
  с подписями под каждым, выбранное значение выделено (обводка/фон).
- `mood · 30d` — гистограмма на 30 дней, каждый бар цвет-кодирован по настроению (зелёный —
  хорошее, жёлтый/оранжевый — среднее, красный/тёмно-оранжевый — плохое), подписи дат по краям
  оси (`MAY 15 … MAY 29 … JUN 13`), справа `AVG · 3.6`.
- `mood × sleep` — горизонтальные полосы-бары по бакетам сна (`< 5h`, `6–7h`, `7–8h`, `8h+`),
  длина бара = средний mood за этот бакет, справа число (`3.8 · 12n`) — среднее и размер выборки;
  сверху текстовый вывод корреляции человеческим языком (`Strong link — better sleep, brighter
  mood.`) — не просто число r, а осмысленная фраза (см. также `[P1-JOURNAL-02]` про честность
  порога — здесь эта же логика должна быть видна визуально: нет данных → нет фразы/бара).
- `today's entry` — `AI · SUMMARY` мелким лейблом сверху, короткое авто-саммари дня текстом,
  затем `Continue writing…` как плейсхолдер основного textarea, счётчик слов справа снизу
  (`0 / n`), кнопка `SAVE ENTRY` капсульная слева снизу.
- Правая колонка — `prompts` с нумерованными подсказками (`02`, `03`…) и `archive` со списком
  последних 10 записей: дата+день недели (`JUN 12 · FRI`), жирный заголовок-саммари одной
  строкой, серый превью текста, ссылка `Show raw` с числом заметок в скобках.

**CRM (скриншот 3):**
- Заголовок `people, moving.` тем же паттерном (акцент вторым словом курсивом-оранжевым).
- Статистика: `6 PEOPLE · 19 TASKS · 3 CONTENT · 7 DECISIONS · 33 CAPTURES`.
- Панель фильтров: инпут поиска на всю ширину `Filter tasks by title, note or tag…` + справа
  ряд текстовых табов-фильтров (`PRIORITY · CATEGORY · KANBAN · ARCHIVE · SMART`) и капсульная
  кнопка `+ NEW`.
- Отдельная строка ниже — быстрый капчур/поиск по смыслу (широкий инпут + кнопка `SEARCH`),

- Карточки задач в канбане — компактные, с цветным бейджем приоритета в правом верхнем углу

Supabase, к Vercel) — честно фиксировать это как «частично» с явным описанием, что именно
осталось непроверенным, а не помечать как «готово».
